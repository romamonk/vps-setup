# VPS Bootstrap для Claude Code — техническое задание для Codex

**Статус:** проектное решение / план реализации, не описание уже настроенного VPS.  
**Дата:** 2026-11-03  
**Цель:** создать Git-репозиторий с воспроизводимой, безопасной и идемпотентной настройкой VPS, предназначенного преимущественно для длительной работы Claude Code через SSH + tmux, с возможностью запускать вспомогательные сервисы на явно заданных портах.

## 1. Контекст и принятые решения

- Основной сценарий — удалённая разработка с Claude Code: работа с Git-репозиториями, Go/Python/Node.js, тестами, сборкой и иногда локальными dev-сервисами. Агент может работать несколько часов после отключения SSH-клиента.
- На том же VPS могут работать PostgreSQL, Redis, API, боты и другие сервисы, преимущественно в Docker; публично доступны только явно выбранные порты.
- **На первом этапе Claude Code работает непосредственно на хосте, без встроенного Claude Sandbox и без контейнеризации самого агента.** Это осознанный компромисс удобства и изоляции.
- Два Linux-пользователя: `admin` (администрирование, `sudo`) и `agent` (Claude Code, **без** `sudo` и без доступа к системному Docker socket/группе `docker`). Имена должны быть конфигурируемыми.
- SSH — только ключи, удалённый root-login отключён; сетевой доступ ограничен firewall. Tailscale/VPN — опциональный последующий этап, не обязательная предпосылка MVP.
- Docker Engine для вспомогательных сервисов администрируется `admin`. Прямой `docker compose` от `agent` **не гарантируется**: это отдельная архитектурная задача, а не повод добавить `agent` в `docker`.
- `tmux` сохраняет сессию и работающий процесс при разрыве SSH, **не** при перезагрузке VPS. Не следует позиционировать tmux как механизм самовосстановления.
- **Не включать `--dangerously-skip-permissions` по умолчанию.** Настраивать разрешения Claude осторожно; полностью unattended-режим — отдельное решение после усиления изоляции.

## 2. Модель угроз и границы безопасности

**Что защищаем:** SSH-доступ, права администратора, системные сервисы Docker, исходники и доступные VPS секреты, стабильность хоста.

**Учитываемые угрозы:** сканирование/подбор SSH, компрометация ключа, вредоносная зависимость, prompt injection в README/исходниках/выводе команд, ошибки автономного агента, случайная публикация БД/Redis, перегрузка CPU/RAM/disk.

**Ограничения MVP (зафиксировать в README и SECURITY.md):**

1. Linux-пользователь **не является песочницей для кода внутри его аккаунта**. Claude и запускаемые им процессы способны читать/изменять всё, что доступно `agent`, включая другие проекты, токены и SSH-ключи.
2. Несколько tmux-сессий или Git worktrees не создают границ безопасности.
3. Permission rules Claude не заменяют OS sandbox; разрешённые команды сборки/тестирования тоже способны запускать произвольный код.
4. Контейнерные порты, публикуемые Docker, могут обходить ожидаемые правила UFW из-за обработки iptables/nftables. Не полагаться только на UFW для защиты опубликованных контейнеров.
5. На MVP не хранить production-секреты и не подключать к агенту критичную production-инфраструктуру.
6. Автономность ограничена подтверждениями, лимитами API/подписки, сбоями сети и перезагрузкой; «работа всю ночь» не гарантирована без отдельной оркестрации.

## 3. Целевая архитектура MVP

```text
MacBook / workstation
   └── SSH keys → [VPS provider firewall] → SSH (key only)
                                          │
Ubuntu Server 24.04 LTS                    │
├── admin (sudo)  ←────────────────────────┘
│   ├── управление OS / пакетами / UFW
│   └── system Docker Engine + Compose
├── agent (no sudo; no system Docker socket)
│   ├── Claude Code (host installation)
│   ├── tmux
│   ├── git, Go/Python/Node.js tools (по необходимости)
│   └── ~/workspace/{project-a,project-b,...}
├── UFW + unattended-upgrades + SSH hardening
└── Docker services (admin-managed)
    ├── PostgreSQL → 127.0.0.1:5432 (пример)
    ├── Redis      → 127.0.0.1:6379 (пример)
    ├── API        → публикация только при необходимости
    └── Bot        → обычно без входящих портов
```

Версия Ubuntu 24.04 LTS — исходное целевое значение, а не требование поддержки единственной версии. Версии Claude Code, инструментов и пакетов определять по актуальным официальным источникам на момент реализации; **не фиксировать непроверенные команды установки**.

## 4. Требования к репозиторию

Рекомендуемый инструмент: **Ansible** для декларативного и повторяемого bootstrap; shell допустим для небольшого локального wrapper, но не как основной большой скрипт с неявными изменениями. Не использовать Terraform, если создание самого VPS через API провайдера пока не входит в scope.

Предлагаемая структура:

```text
vps-bootstrap/
├── README.md
├── SECURITY.md
├── AGENTS.md                  # инструкции для Codex в этом репозитории
├── .gitignore
├── ansible.cfg
├── requirements.yml          # только реально нужные collections/roles
├── inventories/
│   ├── example/hosts.yml
│   └── example/group_vars/all.yml
├── playbooks/
│   ├── bootstrap.yml          # admin, SSH, доступ, firewall — с защитой от lockout
│   ├── configure.yml          # packages, updates, agent, tmux, tools
│   └── docker.yml             # опционально, отдельно от базовой настройки
├── roles/
│   ├── users/
│   ├── ssh_hardening/
│   ├── firewall/
│   ├── updates/
│   ├── dev_tools/
│   ├── tmux/
│   ├── claude_code/
│   └── docker_host/
├── templates/
│   └── ssh_config.example
├── examples/
│   └── compose.local-services.yml
└── tests/
    └── ...                   # lint + проверки итогового состояния
```

Это **предложение структуры**, Codex вправе упростить его без потери требований.

### Качества реализации

- **Idempotent:** повторный прогон не создаёт дубликаты пользователей, правил UFW, строк SSH-конфига, директорий и т.д.
- **Parameterized:** адреса, пользователи, SSH authorized keys, порт SSH, allowlist IP/CIDR, набор пакетов, открываемые сервисные порты — через inventory/vars, без захардкоженных персональных значений.
- **Secure defaults:** непубличные сервисы по умолчанию, root SSH off, password auth off **только после проверки входа по ключу**, без автоматического назначения agent административных прав.
- **Auditable:** изменения выводятся в лог Ansible; секреты маскируются (`no_log`), не попадают в репозиторий и shell-history.
- **Minimal:** не устанавливать Kubernetes, Vault, мониторинговый стек и обязательную контейнеризацию Claude в MVP.
- **Reversible where possible:** изменения документируются; перед опасными операциями — явные preflight checks и recovery plan через консоль провайдера.

## 5. Этапы настройки и критерии приёмки

### Этап 0 — preflight и доступ

1. Подтвердить провайдера, конфигурацию VPS, ОС, исходного пользователя, наличие консоли/recovery у провайдера, публичный IP и разрешённые CIDR для SSH.
2. Проверить локальный SSH-ключ и организовать административное подключение.
3. Сохранить способ доступа через консоль провайдера на случай ошибки firewall/SSH.
4. **Не закрывать текущую SSH-сессию до успешного входа по новому каналу.**

**Acceptance:** доступна как минимум одна проверенная административная SSH-сессия и recovery-путь.

#### Первый запуск с учётными данными провайдера

- Шаблон должен поддерживать исходный SSH-вход как по ключу, так и по логину и паролю провайдера. Исходный пользователь — root либо пользователь с рабочим sudo; адрес, порт и имя задаются в локальном inventory.
- SSH-пароль и, если требуется, отдельный sudo-пароль вводятся интерактивно при запуске. Не передавать их в чате, аргументах команд, inventory, Git или логах. Если среда запуска не поддерживает такой ввод, описать запуск из локального терминала владельца.
- Предусмотреть поиск публичных ключей на управляющем компьютере в `~/.ssh/*.pub` и возможность явно задать другой путь. При нескольких ключах владелец выбирает нужный; при отсутствии ключей требуется отдельное решение о создании нового. Не перезаписывать существующие ключи.
- Выбранные публичные ключи передаются через `admin_authorized_keys` и `agent_authorized_keys` в локальном inventory. Поддерживать отдельные ключи для пользователей; один ключ для обоих допустим по выбору владельца. Приватный ключ остаётся на управляющем компьютере, не копируется на VPS и не выводится в лог; проверить возможность его использования локально или через SSH-agent.
- После создания пользователей проверить отдельными новыми SSH-соединениями вход по ключу для `admin` и `agent`, без fallback на пароль и без переиспользования исходного соединения. Для `admin` также проверить рабочее повышение прав через sudo. До успешных проверок не отключать исходный доступ и не включать firewall.
- После проверки переключить локальный inventory на `admin` и аутентификацию по ключу. Повторные прогоны выполняются этим способом без исходного пароля провайдера; sudo-пароль, если он нужен, по-прежнему запрашивается интерактивно.

**Acceptance:** описан и проверен переход от исходного парольного входа к повторному Ansible-прогону через `admin` по ключу; исходный вход по ключу также поддержан. При неуспешной проверке нового доступа hardening не выполняется, исходный канал остаётся доступным. README содержит оба сценария запуска и порядок выбора ключей без персональных значений.

### Этап 1 — пользователи и SSH

- Создать `admin` с sudo и ключевой аутентификацией; создать `agent` без sudo и без группы `docker`.
- Установить authorized keys управляемо и с правильными правами `.ssh` и `authorized_keys`.
- Запретить root SSH login, парольную и keyboard-interactive аутентификацию; сохранить PubkeyAuthentication.
- Использовать управляемый drop-in `/etc/ssh/sshd_config.d/` **с учётом порядка чтения и first-value-wins**. Не предполагать, что drop-in автоматически побеждает cloud-init/provider snippets.
- Проверять `sshd -t` и *эффективную* конфигурацию `sshd -T` (при `Match` — `-C`), прежде чем reload.
- Настройки forwarding (TCP/agent/X11) выбирать с учётом SSH-туннелей: `AllowTcpForwarding no` по умолчанию не устанавливать без решения, поскольку может понадобиться доступ к БД через `ssh -L`.

**Acceptance:** `admin` и `agent` могут войти по ключу; парольный вход и root SSH запрещены; `agent` не имеет sudo; авторизованные SSH-туннели работают, если включены политикой.

### Этап 2 — firewall и обновления

- UFW: default deny incoming; разрешить SSH **до** включения firewall; публичные порты — только явный allowlist vars.
- Предпочитать одновременно firewall провайдера (если он есть), особенно для контейнерных портов.
- Не открывать 5432/6379 публично. Для Docker публиковать dev DB/Redis на `127.0.0.1` (либо не публиковать на хост вообще).
- Установить и корректно настроить `unattended-upgrades`, проверить включение по фактической apt-конфигурации, а не только по статусу systemd service.
- fail2ban для SSH — опционально; при установке проверить, что sshd jail действительно читает нужный backend/journal.

**Acceptance:** тестовый внешний скан показывает только разрешённые порты; PostgreSQL/Redis недоступны извне; автоматические security updates настроены.

### Этап 3 — dev environment + Claude Code

- Установить `git`, `tmux` и минимальный набор CLI; Go/Python/Node.js — конфигурируемо по потребности, без лишних глобальных установок.
- Установить Claude Code **официальным актуальным способом** под пользователем `agent`; проверять происхождение установщика, избегать непросмотренного `curl | bash` как слепого шаблона.
- Создать `/home/agent/workspace`, обеспечить права доступа и штатный shell.
- Авторизацию Claude Code выполнять **интерактивно**, без помещения API/OAuth-токенов в Ansible inventory, Git, логи и `env | grep`.
- Не настраивать автозапуск Claude при reboot без отдельного требования.
- Не включать глобально `--dangerously-skip-permissions`; не разрешать необдуманно все Bash-команды.

**Acceptance:** `agent` может запустить `claude` в tmux, работать с тестовым репозиторием, после отключения SSH повторно войти в ту же сессию.

### Этап 4 — Docker для сервисов (опционально в MVP)

- Docker Engine/Compose — на хосте под администрированием `admin`.
- **Нельзя** выдавать пользователю `agent` доступ к rootful Docker daemon (`docker` group, `/var/run/docker.sock`, `sudo docker`), поскольку это может дать контроль уровня root над VPS.
- Примеры Compose: DB/Redis с bind `127.0.0.1`, внешний API — только отдельным осознанным решением.
- Для публичных API — reverse proxy с TLS на 80/443 при необходимости; не публиковать внутренние контейнеры напрямую без нужды.
- Тестировать реальную доступность Docker-портов с внешнего хоста: правила Docker и UFW взаимодействуют нетривиально.
- Доступ агента к БД осуществляется через обычный TCP с отдельными минимальными dev credentials, а не через Docker socket.

**Acceptance:** сервисы доступны только из ожидаемых сетей/интерфейсов; `agent` не управляет системными контейнерами.

### Этап 5 — эксплуатация

- Документировать SSH aliases (`vps-admin` и `vps-agent`) и команду:

  ```bash
  ssh -t vps-agent 'tmux new-session -A -s claude'
  ```

- В tmux: `cd ~/workspace/<project> && claude`; detach `Ctrl+B`, затем `D`.
- Для параллельных задач — отдельные tmux-сессии и Git worktrees; понимать, что это логическая, а не security-изоляция.
- Включить базовую диагностику места на диске, памяти и доступных обновлений; определить процесс восстановления после reboot.
- Настроить backup нужных файлов/проектов **вне VPS** либо убедиться, что всё критичное регулярно пушится в Git; хранение только на одном VPS не считается резервным копированием.

**Acceptance:** README содержит запуск, переподключение, проверку и минимальные процедуры восстановления.

## 6. Пример параметров, которые должны быть конфигурируемыми

```yaml
# Пример интерфейса параметров — не готовый production inventory
admin_user: admin
agent_user: agent
ssh_port: 22
ssh_allowed_cidrs: []          # пустое значение требует явного решения о политике SSH
public_tcp_ports: []          # никакие дополнительные порты не открыты по умолчанию
install_docker: false
install_fail2ban: true
install_claude_code: true
install_go: false
install_python_tools: false
install_nodejs: false
agent_workspace_dir: /home/agent/workspace
```

Не хранить реальные private keys, API keys, OAuth tokens, пароли БД, личные адреса и иные секреты в tracked inventory.

## 7. Проверки безопасности, которые Codex должен автоматизировать/описать

- Проверить `sshd -t`, эффективные значения `sshd -T`, корректность подключения под обоими пользователями.
- `id agent` / `sudo -l -U agent`: отсутствие административных полномочий.
- `stat` на `.ssh`, `authorized_keys`, домашнюю директорию и workspace.
- `ufw status verbose`, фактические listening sockets через `ss -lntup`.
- Для Docker — `docker ps --format ...` и тест внешней доступности опубликованных портов (изнутри VPS недостаточно).
- Проверка конфигурации unattended-upgrades; проверка fail2ban jail, если он установлен.
- `tmux ls`, создание/attach/detach и переподключение через второй SSH-сеанс.
- Повторный прогон Ansible и анализ `changed=0` там, где состояние уже достигнуто.
- Lint и syntax checks в CI; по возможности Molecule/VM tests для безопасной проверки конфигурации.

## 8. Что **не** входит в MVP

- Запуск Claude Code внутри Docker/Podman/VM.
- Встроенный Claude Sandbox и настройка сетевых/filesystem policies.
- Полностью автономный режим без ограничений/подтверждений и собственный supervisor агента.
- Rootless Docker под `agent` для самостоятельного `docker compose up`.
- Мультиагентная security-изоляция, раздельные Unix-аккаунты на каждый проект.
- Kubernetes, Vault, полноценная monitoring/logging-платформа.
- Автоматическое создание VPS через Terraform/provider API.
- Установка production БД и перенос реальных production-секретов.

## 9. Возможные расширения после MVP

1. **Встроенный Claude Sandbox:** уточнить по **актуальной** документации поддерживаемые Linux-механизмы, правила доступа к файлам и сети, ограничения Docker CLI/localhost и инструменты, остающиеся вне sandbox.
2. **Rootless Docker под агентом:** если агенту действительно нужен самостоятельный `docker compose up` без rootful socket.
3. **Отдельные контейнеры/VM для агентов:** если появятся unattended-режим, недоверенные репозитории или требования сильной изоляции.
4. **Tailscale:** private-only SSH; после проверки подключения закрыть публичный SSH.
5. **Resource limits и watchdog:** ограничения CPU/RAM/disk и прозрачное наблюдение за длинными задачами.
6. **Отдельные agent-пользователи per project:** при необходимости изоляции проектов и credentials друг от друга.

## 10. Задание Codex (можно использовать как стартовый prompt)

> Создай в этом репозитории воспроизводимый Ansible-based bootstrap Ubuntu VPS по спецификации `VPS_CLAUDE_CODE_BOOTSTRAP_SPEC.md`. Начни с краткого плана и перечисления решений, которые требуют значений inventory. Реализуй минимально достаточную структуру, SSH/users/firewall/update roles, dev environment и опциональный Docker-host. Подготовь README с пошаговым безопасным первым запуском и recovery-процедурой. Не допускай блокировки SSH: проверка admin key-login должна предшествовать отключению паролей/root и включению firewall. `agent` без sudo и без system Docker socket. Не добавляй секреты, публичные порты, `--dangerously-skip-permissions` или sandbox/containerization Claude без отдельного решения. Добавь линтеры, syntax checks и проверяемые acceptance criteria. Не выполняй реальные изменения на VPS без явного указания пользователя. Перед использованием команд установки Claude Code сверяй их с актуальной официальной документацией. Зафиксируй все предположения и ограничения безопасности.

## 11. Открытые вопросы перед применением к реальному VPS

- Провайдер и образ ОС; новый VPS или уже используемый?
- Публичный IPv4/IPv6, провайдерский firewall и recovery console?
- Статический адрес клиента или динамический; SSH публичный или через Tailscale?
- Нужны ли `ssh -L` и другие TCP-forwarding возможности?
- Какие публичные сервисы и TCP/UDP-порты действительно нужны?
- Какие toolchains нужны сразу (Go, Python, Node.js), какие версии?
- Нужна ли Claude Code аутентификация через подписку или API, и как вручную пройти login?
- Нужен ли агенту собственный rootless Docker позднее?
